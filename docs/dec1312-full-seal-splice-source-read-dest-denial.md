# DEC-1312 — Full memfd seals deny splice destination writes, not source reads

Direct local Linux syscall probe verified: create 23-byte generated PUBLIC memfd, install a genuine **anonymous original inode-only** inotify watcher through `/proc/self/fd/<memfd>`, apply `F_SEAL_WRITE|F_SEAL_GROW|F_SEAL_SHRINK|F_SEAL_SEAL` and read back the exact seal set with F_GET_SEALS. Real `os.splice(sealed_memfd,pipe_writer,full_length,offset_src=0)` **succeeds** and transfers all original source bytes to the pipe; the original memfd remains byte-equal, size-equal and its native mutation queue empty. This is a *read*, not a data-integrity violation.

Reverse the same syscall direction: stage four generated PUBLIC bytes in the pipe, then call `os.splice(pipe_reader,sealed_original_fd,4,offset_dst=0)`. This would write into the original sealed memfd. The kernel correctly denies it with **EPERM**, original data/length/seals stay identical, and the genuine original anonymous inode's mutation watcher remains quiet. The same four bytes can still be read from the pipe following rejection, verifying no partial payload consumption. Closing the memfd retires original kernel inode watch with native DELETE_SELF/IGNORED. This is a positive enforcement demonstration **only for this exact tested anonymous inode and syscall**.

The security distinction is syscall direction and original source integrity: full WRITE/GROW/SHRINK/SEAL enforces the tested memfd destination-write rejection but does **not** prohibit reading data already accessible through the original file handle, nor imply a confidentiality guarantee.
