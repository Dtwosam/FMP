An independent genuine Linux probe verified the precise sequence. Create original anonymous PUBLIC 23-byte `memfd_create(MFD_ALLOW_SEALING)` and watch the actual memfd inode via native inotify on `/proc/self/fd/<memfd>`. Open a **real writable MAP_SHARED mapping** while no seal exists. Attempt `fcntl(F_ADD_SEALS,F_SEAL_WRITE)` with that mapping alive: the kernel rejects **EBUSY**, confirming the strict write seal cannot be applied while a writable mapping already exists. `F_GET_SEALS` remains zero and the original backing content is unchanged.

Next `F_ADD_SEALS(F_SEAL_FUTURE_WRITE)` **succeeds** despite the outstanding writable mapping. A new `pwrite` and a **new** writable MAP_SHARED mapping reject **EPERM**, but the **preexisting** writable MAP_SHARED can still change and restore **actual original memfd backing bytes**, independently verified by real `pread`, with **no native memfd IN_MODIFY** for either shared mapped data write. Even while FUTURE_WRITE seal is active, trying to add the strong `F_SEAL_WRITE` continues to reject EBUSY until the old writable shared mapping is explicitly closed. Only after that unmap can the strict write seal be added, along with GROW/SHRINK. Exact F_GET_SEALS bitset, blocked file growth/shrink, original bytes/size, negative inotify receipts and final inode DELETE_SELF/IGNORED are checked.
