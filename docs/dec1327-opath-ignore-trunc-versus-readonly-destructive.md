# DEC-1327 — O_PATH ignores O_TRUNC, but true O_RDONLY open can truncate data

**DRAFT / NEVER MERGE / NEVER PROMOTE.** Strict one-commit child of #1550 DEC-1326 at `ae1635adbb8116702d96a3a520ced51327f4ec14`, proposed **884 distinct source-defined test methods**. Two generated PUBLIC anonymous Linux memfd inodes (one WRITE-only sealed, the other fully WRITE|GROW|SHRINK|SEAL sealed); real native inode-only watches, no named original parent.

A native local Linux probe confirmed that opening `/proc/self/fd/<memfd>` with **O_PATH|O_TRUNC**, including `O_PATH|O_WRONLY|O_TRUNC`, **succeeds without truncating**: O_PATH makes the O_TRUNC and ordinary read/write access flags inapplicable to that path-only descriptor. The source remains original bytes/size, and genuine inotify IN_MODIFY remains quiet; `pread(O_PATH_fd)` rejects EBADF. This holds even when only F_SEAL_WRITE protects the memfd—and also under full data/size seals.

In contrast, opening the **same weakly sealed original inode** with *actual* **O_RDONLY|O_TRUNC** (without O_PATH) truly deletes all original bytes, reduces size to zero and emits native IN_MODIFY. On the fully sealed original inode the same real O_RDONLY|O_TRUNC operation rejects EPERM, leaves original bytes/size untouched, and emits no MODIFY. Exact native F_GET_SEALS, original inode dev/ino, source bytes and lifecycle DELETE_SELF/IGNORED are verified independently.

**Security interpretation:** Neither a successful `open` nor a nominal O_RDONLY/O_WRONLY bit proves content access or data modification without considering `O_PATH` and `O_TRUNC`.
