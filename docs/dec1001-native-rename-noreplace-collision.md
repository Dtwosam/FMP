# DEC-1001 — Atomic RENAME_NOREPLACE collision does not mutate watched symlink inodes

**DRAFT / NEVER MERGE / NEVER PROMOTE.** Strict test/documentation child of DEC-1000/#1221, using only generated public Linux /tmp fixtures.

A genuine native `renameat2(RENAME_NOREPLACE)` operation tries to move one symlink over another existing symlink. Both entries have separate watched link inodes (`IN_DONT_FOLLOW | IN_MOVE_SELF | IN_DELETE_SELF`) alongside the original source and parent inotify registrations. Linux must reject the operation with `-1/EEXIST`, emit no rename or link-invalidation event, and leave both dev/inode identities and native subscriptions intact. Real write-through-alias operations still reach the original source `IN_MODIFY` and parent named `sample` records, with the unchanged evaluator `BLOCKED`, `can_authorize_dispatch=false`, and `independent_os_proof_verified=false`.

The control then unlinks **only** the conflicting destination, expecting its own link-WD `IN_DELETE_SELF` and `IN_IGNORED`. Repeating the identical RENAME_NOREPLACE call now succeeds, emits genuine parent `IN_MOVED_FROM`/`IN_MOVED_TO` with matching nonzero cookie and source-link `IN_MOVE_SELF`, and preserves the source link inode at the destination pathname. Deleting it finally invalidates its original WD. This is distinct from DEC-998's successful `RENAME_EXCHANGE`: the atomic **failure** path cannot be misread as a rename event or a new trust boundary.

A standalone native Linux probe confirmed `EEXIST`, an empty queue after the rejected operation, surviving watch identities, the later successful move cookie pair and link invalidations.
